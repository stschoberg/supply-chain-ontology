# Data engineering

How the [data releases](README.md) are built: extract and load real-world sources, transform them with
dbt in DuckDB, package the published tables, and lift them into RDF ([mappings](mappings/README.md)).

```
sources/<source>/fetch.py ──► sources/<source>/raw/ ──► transform/ (dbt) ──► release.py ──► GitHub release
        extract + load              snapshots             staging, meta        Parquet + catalog
                                                               └──► mappings/ ──► graph/ (RDF)
```

```bash
make fetch-usaspending    # E + L: download a snapshot
make transform            # T: dbt build (models + data tests) into data/warehouse.duckdb
make dist                 # package a release in data/dist/
make lift                 # lift data/dist/'s tables into RDF in data/graph/: source terms, then each model's
make data-docs            # regenerate DICTIONARY.md after editing a published model's YAML
```

## Layout

```
data/
  README.md                 # for consumers: what's in the data and how to use it
  DICTIONARY.md             # generated from the published models' YAML (make data-docs)
  data.mk                   # make targets, included by the root Makefile (run from the repo root)
  sources/<source>/
    README.md               # license, cadence, access, columns we use, gaps, quirks
    fetch.py                # uv run python -m data.sources.<source>.fetch
    raw/<snapshot-date>/    # downloaded files, untouched, + .manifest.json (gitignored)
  transform/                # dbt project (see its README)
  dictionary.py             # renders the published tables' descriptions
  examples/explore.ipynb    # Colab notebook for consumers; tests run it against a fixture release
  release.py                # packages published models as a release (make dist)
  warehouse.duckdb          # dbt output (gitignored)
  dist/                     # release output (gitignored)
  lift.py                   # runs the mappings over a release's tables (make lift)
  mappings/<source>/        # tables → RDF in the source's terms, then into a model's (see its README)
  graph/                    # lift output (gitignored)
```

## The published interface

A dbt model tagged `published` is part of the data product. Its YAML must give the table and every
column a `description` and a `data_type`, under an enforced contract. Those descriptions are written
once and reach consumers four ways:

- `DICTIONARY.md`, regenerated by `make data-docs`. A test fails if it's stale.
- Each release's notes.
- The Parquet files' key-value metadata (`description`, `column_descriptions`).
- `COMMENT ON` for each view and column in `catalog.duckdb`, visible in `duckdb_columns()`.

Removing or retyping a published column is a breaking change; call it out in the release notes.

## Data releases

A release is a GitHub Release tagged `data-YYYY-MM-DD`, or `data-YYYY-MM-DD.2`, `.3`, ... for later
releases the same day:

| Asset | What it is |
|---|---|
| `<table>.parquet` | One file per published model. **The data.** Readable by any tool. |
| `<table>.csv` | The same rows as CSV, for spreadsheets. |
| `catalog.duckdb` | Views over those Parquet files, so DuckDB users can `attach` and see named, commented tables. Holds no data. |
| `<source>.nt.gz` | The same rows as an RDF graph in the source's own terms, lifted by the [mappings](mappings/README.md). |
| `<source>.vocabulary.ttl` | The classes and properties that graph uses, each with a label and definition. A copy of the source's `vocabulary.ttl` in [mappings](mappings/README.md). |
| `<source>.<target>.experimental.nt.gz` | That graph mapped into another ontology's terms, e.g. `iof-scro`. Experimental: the mapping is incomplete and will change. |
| `raw-<source>-<snapshot>.tar` | The raw source files the tables were built from, for exact reproduction. |
| `RELEASE_NOTES.md`, `SHA256SUMS` | How to connect, row counts, the data dictionary, provenance, checksums. |

**Publishing:** run the [Data release](../.github/workflows/data-release.yml) workflow from the Actions tab
(main only). It fetches fresh snapshots, runs `make dist` (any failing dbt data test stops it), then
`python -m data.release publish`:

1. Creates the dated release with the Parquet files, raw archive, and notes.
2. Builds the catalog against those now-live URLs and uploads it. DuckDB checks a view's files when it
   creates the view, so this can't happen earlier.
3. Attaches the published catalog from a fresh session and checks the row counts.
4. Recreates `data-latest` with the same files.

It refuses to overwrite an existing tag or to publish a build of uncommitted code.

## Adding a source

1. `sources/<source>/README.md` (copy the USAspending one's metadata table) and `fetch.py`, writing
   immutable snapshots with manifests.
2. A dbt source, a `stg_<source>__<thing>` model with data tests, and a fixture-based test in `tests/`.
3. To publish it: tag the model `published`, give it a contract with descriptions, run `make data-docs`,
   and add it to `SOURCES` in `release.py` and to the table list in [README.md](README.md).

## Fetching well

- **Prefer bulk downloads over search APIs.** Search APIs return fewer fields and paginate. Fetch whole
  records and narrow them during staging.
- **Raw files are immutable snapshots.** A refetch goes in a new snapshot directory, never over an old one.
- **Verify what came back:** that the server applied our filters, that row counts match, and that the
  columns we depend on exist. Fail loudly otherwise.
- **Keep API keys in environment variables** (or a gitignored `.env`), never in the repo.
- **Shared plumbing** (retries, User-Agent, OS certificate store, manifests) lives in `src/sco/fetching.py`.
